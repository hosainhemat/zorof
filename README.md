# ظرف من — راهنمای کامل (نسخه نهایی، تک‌مدیر)

> این پروژه در ۶ مرحله به یک فروشگاه تک‌مدیره تبدیل شد. تاریخچه کامل هر مرحله پایین همین فایل است؛ این بخش بالا فقط **خلاصه وضعیت نهایی** است که برای نصب/استقرار کافی‌ست.

## ساختار نهایی فایل‌ها
| فایل | نقش |
|---|---|
| `index.html` + `app.js` + `style.css` | فروشگاه (سمت مشتری) |
| `admin.html` + `admin.js` | پنل مدیر — محصولات، سفارش‌ها، مشتریان، اعتبار، تنظیمات، همه‌چیز |
| `accounting.html` + `accounting.js` + `accounting.css` | ماژول حساب‌داری عمده‌فروشی (اشخاص، اسناد، چک) |
| `supplier.css` | فایل استایل **مشترک** بین فروشگاه/مدیر/حساب‌داری — با وجود اسمش حذف نشود |
| `firebase-config.js` | کلیدهای Firebase + Cloudinary + شماره نسخه برنامه |
| `jalali.js` | تبدیل تاریخ میلادی به شمسی |
| `cities.js` | لیست شهرهای ایران |
| `manifest.json` + `sw.js` + `icon-*.png` | تنظیمات PWA (نصب روی گوشی) |
| `README.md` | همین فایل |

**فایل‌هایی که دیگر وجود ندارند (حذف‌شده در مرحله ۶):** `supplier.html`, `supplier.js` — اگر هنوز در گیت‌هاب شما هستند، حذفشان کنید.

## قدم‌های نصب از صفر (یا جایگزینی کامل)
1. همه فایل‌های این زیپ را در ریپازیتوری گیت‌هاب خودتان جایگزین کنید (و `supplier.html`/`supplier.js` قدیمی را اگر مانده، حذف کنید).
2. در Firebase Console → Firestore Database → Rules، آخرین نسخه قوانین (پایین همین فایل، زیر عنوان «مرحله ۱») را Publish کنید.
3. مطمئن شوید سند `admins/{uid}` خودتان، و `settings/site` (شهر/موقعیت فروشگاه) تنظیم شده‌اند — از پنل مدیر → تنظیمات.
4. وارد `admin.html` شوید؛ از همان‌جا محصول اضافه کنید، سفارش بگیرید، پرداخت تایید کنید.

## خلاصه قابلیت‌ها
- مدیریت کامل محصول: چند عکس، فیلد دلخواه نامحدود، موجودی (هرگز به مشتری عدد نشان داده نمی‌شود)، دسته‌بندی پویا، برچسب «شگفت‌انگیز»
- سفارش: قبول/رد، تایید/رد پرداخت (فیش بانکی یا چک، با دلیل رد برای مشتری)، وضعیت صیادی چک
- خرید اعتباری با سقف پنهان، بازپرداخت با تایید مدیر
- دفترچه تلفن مشتریان با نام قابل‌ویرایش و موقعیت به‌صورت نوشتار (تبدیل خودکار GPS با سرویس رایگان)
- حساب‌داری عمده‌فروشی جدا: اشخاص، اسناد بدهکار/بستانکار، چک با سررسید شمسی
- تم رنگی/مشکی قابل‌تعویض، پشتیبان‌گیری CSV، بازنشانی داده‌های آزمایشی (تکی یا کامل)
- PWA قابل‌نصب روی گوشی، با Service Worker «اول شبکه» (همیشه نسخه تازه می‌گیرد)

# فروشگاه ظروف — نسخه اول (PWA)

## ساختار فایل‌ها (همه در یک سطح، بدون پوشه فرعی)
- `index.html` — صفحه اصلی
- `style.css` — استایل‌ها
- `app.js` — منطق محصولات و سبد خرید
- `manifest.json` — تنظیمات نصب اپ
- `sw.js` — کش آفلاین
- `icon-192.png`, `icon-512.png` — آیکون‌های اپ (فعلاً نمونه، بعداً با لوگوی خودتان جایگزین کنید)

## مرحله ۱: بالا بردن روی گیت‌هاب (روش رایگان، فقط با Safari)
1. فایل زیپ را در اپ Files، Unzip کنید تا این ۷ فایل را جدا ببینید.
2. در Safari به آدرس github.com بروید و وارد حساب خود شوید.
3. روی علامت **+** بالای صفحه بزنید → **New repository**.
4. اسم را `zorof-shop` بگذارید (Public یا Private فرقی ندارد) و **Create repository** را بزنید.
5. در صفحه‌ی خالی ریپازیتوری، گزینه **uploading an existing file** را بزنید (یک لینک آبی وسط صفحه است).
6. روی کادر آپلود بزنید تا کیبورد و انتخاب‌گر فایل باز شود؛ به پوشه‌ای که Unzip کردید بروید.
7. همه‌ی ۷ فایل را با هم انتخاب کنید (روی یک فایل لمس طولانی بزنید → Select → بقیه را هم لمس کنید تا انتخاب شوند) و **Open/Add** را بزنید.
8. پایین صفحه دکمه سبز **Commit changes** را بزنید.

اگر بعداً خواستید فایلی را عوض کنید (مثلاً `app.js` را ویرایش کنید)، در گیت‌هاب روی همان فایل بزنید، آیکون مداد (Edit) را بزنید، تغییر بدهید و دوباره Commit کنید — نیازی به آپلود دوباره همه‌چیز نیست.

## مرحله ۲: فعال کردن GitHub Pages
1. در سایت گیت‌هاب، وارد ریپازیتوری شوید.
2. Settings → Pages
3. از قسمت Branch گزینه `main` و پوشه `/ (root)` را انتخاب کنید و Save بزنید.
4. بعد از حدود یک دقیقه، آدرسی شبیه این فعال می‌شود:
   `https://USERNAME.github.io/zorof-shop/`

## مرحله ۳: نصب روی آیفون
1. آدرس بالا را در Safari باز کنید.
2. دکمه Share را بزنید → Add to Home Screen.
3. حالا اپ مثل یک اپ واقعی روی گوشی نصب است.

## مرحله بعد
- افزودن درگاه پرداخت (زرین‌پال) — این بخش نیاز به یک سرویس کوچک سمت سرور دارد
- تبدیل به APK برای اندروید (با ابزار Bubblewrap یا PWABuilder)

# پنل تامین‌کنندگان (دیتابیس محصولات)

از این به بعد، محصولات دیگر داخل کد نوشته نمی‌شوند — هر تامین‌کننده با حساب خودش وارد `supplier.html` می‌شود و محصولات را اضافه/ویرایش/حذف می‌کند و همان لحظه در فروشگاه دیده می‌شود.

فایل‌های جدید: `firebase-config.js`, `supplier.html`, `supplier.css`, `supplier.js`
فایل‌های تغییر‌کرده: `index.html`, `app.js`, `style.css`

## مرحله ۱: ساخت پروژه Firebase (رایگان)
1. در Safari به آدرس **console.firebase.google.com** بروید و با همان حساب گوگل خود وارد شوید.
2. **Add project** (یا Create a project) را بزنید.
3. یک اسم بدهید، مثلاً `zorof-shop`، و مراحل را تا آخر با تنظیمات پیش‌فرض جلو بروید (Google Analytics را می‌توانید خاموش کنید، لازم نیست).

## مرحله ۲: فعال کردن ورود با ایمیل
1. در پنل پروژه، از منو سمت چپ **Build → Authentication** را باز کنید.
2. **Get started** را بزنید.
3. از لیست روش‌ها، **Email/Password** را انتخاب و **Enable** کنید، سپس Save.

## مرحله ۳: ساخت دیتابیس Firestore
1. از منو **Build → Firestore Database** را باز کنید.
2. **Create database** را بزنید.
3. حالت **Production mode** را انتخاب کنید (نه Test mode) و یک منطقه (Location) نزدیک، مثلاً `eur3` یا پیش‌فرض را بزنید → Enable.
4. بعد از ساخته‌شدن دیتابیس، به تب **Rules** بروید، متن داخلش را پاک کنید و این را جایگزین کنید:

> این قوانین نسخه نهایی هستند (شامل تایید تامین‌کننده، صف سفارش‌ها و پیام‌رسانی). اگر قبلاً نسخه قدیمی‌تری گذاشته‌اید، همین را کامل جایگزین کنید.

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    function isAdmin() {
      return request.auth != null &&
        exists(/databases/$(database)/documents/admins/$(request.auth.uid));
    }

    match /products/{productId} {
      allow read: if resource.data.status == 'approved' || isAdmin();
      allow create, update, delete: if isAdmin();
    }

    match /admins/{uid} {
      allow read: if request.auth != null && request.auth.uid == uid;
      allow write: if false;
    }

    match /orders/{orderId} {
      allow create: if true;
      allow read: if isAdmin()
        || (request.auth != null && resource.data.buyerUid == request.auth.uid);
      allow update: if isAdmin()
        || (request.auth != null && resource.data.buyerUid == request.auth.uid
            && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['creditSettlement']));
      allow delete: if isAdmin();
    }

    match /categories/{categoryId} {
      allow read: if true;
      allow write: if isAdmin();
    }

    match /settings/{docId} {
      allow read: if true;
      allow write: if isAdmin();
    }

    match /acc_persons/{id} {
      allow read, write: if isAdmin();
    }
    match /acc_transactions/{id} {
      allow read, write: if isAdmin();
    }
    match /acc_checks/{id} {
      allow read, write: if isAdmin();
    }

    match /trustedCustomers/{phone} {
      allow get: if true;
      allow list, write: if isAdmin();
    }

    match /customers/{phone} {
      allow read, write: if isAdmin();
    }

    match /creditAccounts/{phone} {
      allow read, write: if isAdmin();
    }

    match /creditFlags/{phone} {
      allow get: if true;
      allow list, write: if isAdmin();
    }
  }
}
```

> **سقف اعتبار و شماره مشتری‌ها دیگر قابل فهرست‌شدن نیست:** سقف واقعی اعتبار فقط در `creditAccounts` است که فقط مدیر و همان تامین‌کننده می‌خوانند. برای اینکه فروشگاه بداند گزینه «خرید اعتباری» را نشان بدهد یا نه، فقط یک سند سبک `creditFlags/{شماره}` (بدون هیچ مبلغی) ساخته می‌شود که فقط با «دانستن شماره» قابل خواندن است، نه فهرست‌کردن.

> نکته امنیتی: چون خریدارها حساب کاربری ندارند، ثبت سفارش (`create`) برای همه باز است — این طبیعی است برای فروشگاهی که مهمان هم می‌تواند سفارش بدهد. اگر بعداً اسپم دیدید، Firebase App Check راه‌حل استاندارد است.

5. **Publish** را بزنید.


## مرحله ۴: راه‌اندازی Cloudinary برای عکس‌ها (بدون نیاز به کارت بانکی)
Firebase Storage الان به کارت بانکی نیاز دارد، پس عکس‌ها را در سرویس رایگان Cloudinary ذخیره می‌کنیم — ثبت‌نامش فقط با ایمیل است.

1. در Safari به آدرس **cloudinary.com** بروید و **Sign up** بزنید (با ایمیل، بدون کارت بانکی).
2. بعد از ورود به داشبورد، بالای صفحه یک مقدار به اسم **Cloud name** می‌بینید — آن را جایی یادداشت کنید.
3. روی چرخ‌دنده تنظیمات (⚙️، بالای صفحه) بزنید → **Upload** را از منوی سمت چپ باز کنید.
4. پایین صفحه بخش **Upload presets** را پیدا کنید و **Add upload preset** را بزنید.
5. گزینه **Signing Mode** را از Signed به **Unsigned** تغییر دهید.
6. یک اسم برای preset بگذارید (مثلاً `zorof_products`) و **Save** بزنید.
7. این دو مقدار را یادداشت کنید: **Cloud name** و اسم **Upload preset** که ساختید.

## مرحله ۵: گرفتن کلیدهای اتصال Firebase
1. در Firebase، روی چرخ‌دنده کنار "Project Overview" بزنید → **Project settings**.
2. پایین صفحه، بخش **Your apps** را پیدا کنید و آیکون **</>** (Web) را بزنید.
3. یک اسم دلخواه بدهید (مثلاً `zorof-web`) و **Register app** را بزنید.
4. یک بلوک کد به شما نشان داده می‌شود شبیه:
```
const firebaseConfig = {
  apiKey: "...",
  authDomain: "...",
  projectId: "...",
  storageBucket: "...",
  messagingSenderId: "...",
  appId: "..."
};
```
5. این مقادیر را کپی کنید.

## مرحله ۶: جایگذاری همه کلیدها در پروژه
1. در گیت‌هاب، فایل `firebase-config.js` را باز کنید و مداد ویرایش (Edit) را بزنید.
2. مقدار `firebaseConfig` را با مقادیری که از Firebase کپی کردید جایگزین کنید.
3. مقدار `CLOUDINARY_CLOUD_NAME` را با Cloud name خودتان و `CLOUDINARY_UPLOAD_PRESET` را با اسم preset که ساختید جایگزین کنید.
4. Commit changes را بزنید.

## مرحله ۷: بالا بردن فایل‌های جدید و تغییرات
در گیت‌هاب:
- فایل‌های **جدید** (`supplier.html`, `supplier.css`, `supplier.js`) را از همان روش قبلی (**Add file → Upload files**) اضافه کنید.
- فایل‌های **تغییر‌کرده** (`index.html`, `app.js`, `style.css`) را با همین روش آپلود مجدد کنید — گیت‌هاب خودش تشخیص می‌دهد که همان فایل قبلی است و آن را جایگزین (overwrite) می‌کند؛ لازم نیست چیزی حذف کنید.

## تست نهایی
1. آدرس سایت خودتان را باز کنید و انتهای آن `supplier.html` اضافه کنید، مثلاً:
   `https://USERNAME.github.io/zorof-shop/supplier.html`
2. ثبت‌نام کنید (نام فروشگاه + ایمیل + رمز)، یک محصول با عکس اضافه کنید.
3. به صفحه اصلی فروشگاه برگردید — باید محصول را آنجا ببینید.

اگر هر کدام از این مراحل گیر کرد، عکس بگیرید و بفرستید تا دقیق راهنمایی کنم.

# پنل مدیر (تایید محصولات)

محصولات تامین‌کنندگان دیگر مستقیم در فروشگاه نمایش داده نمی‌شوند — ابتدا با وضعیت «در انتظار تایید» ثبت می‌شوند و فقط بعد از تایید شما در `admin.html` در فروشگاه دیده می‌شوند.

فایل‌های جدید: `admin.html`, `admin.js`
فایل تغییر‌کرده: `supplier.js`, `supplier.css`, `app.js`، و قوانین Firestore (بالا به‌روز شد — دوباره Publish کنید)

## ساخت حساب مدیر (خودتان)
1. یک ایمیل و رمز عبور برای خودتان به‌عنوان مدیر در نظر بگیرید (می‌تواند همان ایمیلی باشد که با Firebase وارد شده‌اید یا یک ایمیل دیگر).
2. فعلاً از همان فرم ثبت‌نام تامین‌کننده در `supplier.html` با این ایمیل ثبت‌نام کنید (نام فروشگاه را هرچه بگذارید فرقی ندارد) — این فقط برای ساخته‌شدن حساب لازم است.
3. در Firebase Console، از منو ☰ → **Security → Authentication** بروید. در تب **Users**، ایمیل خودتان را پیدا کنید و ستون **User UID** را کپی کنید.
4. از منو ☰ → **Databases & Storage → Firestore Database** بروید، تب **Data**.
5. **Start collection** (یا Add collection) را بزنید، اسم کالکشن را `admins` بگذارید.
6. برای **Document ID**، همان UID که کپی کردید را جای‌گذاری کنید (نه اسم دلخواه — دقیقاً همان UID).
7. یک فیلد اضافه کنید: نام فیلد `email`، نوع `string`، مقدار ایمیل خودتان → Save.

## استفاده
آدرس `https://USERNAME.github.io/zorof-shop/admin.html` را باز کنید، با همان ایمیل/رمز وارد شوید. محصولات «در انتظار تایید» را می‌بینید — با دکمه **تایید** یا **رد کردن** برایشان تصمیم بگیرید. فقط محصولات تایید‌شده در فروشگاه اصلی دیده می‌شوند.

## تست نهایی
1. با یک حساب تامین‌کننده (غیر از حساب مدیر) یک محصول اضافه کنید — باید در فروشگاه دیده **نشود**.
2. با حساب مدیر در `admin.html` وارد شوید و آن را تایید کنید.
3. به فروشگاه اصلی برگردید — محصول باید ظاهر شود.

# موقعیت مکانی، انتخاب شهر و سفارش‌ها

فایل‌های جدید: `cities.js`
فایل‌های تغییر‌کرده: `index.html`, `app.js`, `style.css`, `supplier.html`, `supplier.js`, `supplier.css` + قوانین Firestore (بالا به‌روز شد — دوباره Publish کنید)

## چطور کار می‌کند
- **تامین‌کننده**: در پنل خودش، شهرش را از لیست انتخاب می‌کند و می‌تواند دکمه «دریافت موقعیت مکانی دقیق» را بزند تا مختصات GPS فروشگاهش ذخیره شود.
- **خریدار**: بالای صفحه فروشگاه، دکمه شهر را می‌زند — یا یک شهر از لیست انتخاب می‌کند (مثل دیوار)، یا «موقعیت مکانی من» را می‌زند تا محصولات بر اساس فاصله دقیق (کیلومتر) مرتب شوند.
- **سفارش**: هنگام ثبت سفارش، شماره تماس خریدار گرفته می‌شود. سفارش برای هر تامین‌کننده جدا ذخیره می‌شود و در بخش «سفارش‌های من» در پنل او (به‌صورت آنی) ظاهر می‌شود — همراه با فاصله تقریبی تا خریدار و یک دکمه تماس مستقیم.
- فعلاً اطلاع‌رسانی فقط داخل پنل است (وقتی تامین‌کننده وارد می‌شود سفارش را می‌بیند). پیامک/پوش‌اعلان فوری یک مرحله بعدی است که نیاز به یک سرویس پیامکی دارد.

## کاری که باید انجام دهید
1. قوانین Firestore بالا را (نسخه جدید، شامل `suppliers` و `orders`) در Firebase → Firestore → Rules جایگزین و Publish کنید.
2. فایل جدید `cities.js` را در گیت‌هاب آپلود کنید.

# نسخه کامل: تایید تامین‌کننده، صف هدایت سفارش، موجودی، گزارش و پیام‌رسانی

این بزرگ‌ترین به‌روزرسانی پروژه است. همه فایل‌ها به‌روز شدند: `index.html`, `app.js`, `style.css`, `supplier.html`, `supplier.js`, `supplier.css`, `admin.html`, `admin.js`, `manifest.json` + قوانین Firestore بالا (نسخه نهایی، حتماً جایگزین کنید).

## خلاصه تغییرات

**۱. تایید تامین‌کننده قبل از فعالیت**
تامین‌کننده جدید هنگام ثبت‌نام، شماره تماس هم می‌دهد و حسابش با وضعیت «در انتظار تایید» ساخته می‌شود. تا شما در تب «تامین‌کنندگان» پنل مدیر او را تایید نکنید، فقط یک پیام «در انتظار تایید» می‌بیند (با امکان پیام دادن به شما) و نمی‌تواند محصول اضافه کند.

**۲. لیست مجزای تامین‌کنندگان و مشتریان (پنل مدیر)**
- تب «تامین‌کنندگان»: تایید/رد/حذف، با شماره تماس هرکدام.
- تب «مشتریان»: از روی سفارش‌ها ساخته می‌شود (چون خریدار حساب ندارد) — شماره، تعداد سفارش، مجموع خرید، با دکمه تماس و واتساپ مستقیم.

**۳. صف هدایت سفارش**
هر سفارش یک لیست اولویت (`queue`) دارد: همیشه شما (مدیر) اول، بعد بقیه تامین‌کنندگان تاییدشده به ترتیب فاصله (نزدیک‌ترین اول؛ در صورت نبود موقعیت GPS، بر اساس هم‌شهر بودن). سفارش **فقط و فقط پیش نفر فعلی صف می‌ماند** — هر چقدر طول بکشد، تا وقتی که او صریحاً قبول یا رد نزند، به هیچ‌کس دیگری نشان داده نمی‌شود:
- **قبول کند** → سفارش قطعی مال او می‌شود و از صف بقیه حذف می‌شود.
- **رد کند** → همان لحظه (بدون تاخیر) به نفر بعدی (نزدیک‌ترین تامین‌کننده بعدی) نمایش داده می‌شود.
- **هیچ‌کاری نکند** → سفارش همچنان فقط پیش او می‌ماند؛ هیچ تایمر خودکاری برای نمایش به نفر بعدی وجود ندارد.
- اگر همه (شامل شما) به‌ترتیب رد کردند → سفارش با وضعیت «بدون پاسخ» به تب «سفارش‌ها»ی پنل مدیر برمی‌گردد تا خودتان دستی آن را تامین کنید.

> صف بر اساس **فاصله دقیق GPS** مرتب می‌شود، نه مرز رسمی استان (که نیاز به نقشه اداری کامل کشور دارد و فعلاً پیاده‌سازی نشده) — در عمل نتیجه مشابهی می‌دهد.

**۴. موجودی کالا**
هنگام افزودن محصول، تامین‌کننده تعداد موجودی را هم وارد می‌کند. مشتری فقط «موجود» یا «ناموجود» می‌بیند (نه عدد دقیق). شما در تب «موجودی» پنل مدیر، موجودی همه محصولات همه تامین‌کنندگان را می‌بینید؛ هر تامین‌کننده هم در پنل خودش فقط موجودی خودش را می‌بیند.

**۵. گزارش عملکرد و درآمد**
- پنل تامین‌کننده، تب «گزارش من»: تعداد سفارش قبول‌شده، رد‌شده، و درآمد خودش.
- پنل مدیر، تب «گزارش»: درآمد کل فروشگاه + تفکیک هر تامین‌کننده (قبول/رد/درآمد).

**۶. پیام‌رسانی داخل برنامه**
یک گفتگوی ساده بین شما و هر تامین‌کننده — هم در پنل تامین‌کننده (تب «پیام با مدیر») هم در پنل مدیر (تب «پیام‌رسانی»، با انتخاب تامین‌کننده از لیست). برای مشتری‌ها چون حساب ندارند، به‌جای چت داخلی، دکمه تماس/واتساپ مستقیم گذاشته شده.

## کاری که باید انجام دهید
1. قوانین Firestore بالا (نسخه نهایی) را Publish کنید.
2. همه فایل‌های تغییر‌کرده را در گیت‌هاب جایگزین کنید.
3. چون منطق ورود عوض شده، **حساب مدیر فعلی خودتان را دوباره چک کنید**: وارد `supplier.html` شوید — اگر پیام «در انتظار تایید» دیدید طبیعی است (چون این حساب هم حالا از این قانون پیروی می‌کند)، ولی چون سند `admins/{uid}` را قبلاً دستی ساختید، در `admin.html` مثل قبل مدیر هستید و از همان‌جا می‌توانید حساب خودتان را در تب «تامین‌کنندگان» approve کنید تا هم به‌عنوان یک تامین‌کننده هم فعال باشید (لازم است چون شما «تامین‌کننده اول» صف هستید).
4. محصولات قبلی خود را یک‌بار ویرایش کنید تا فیلد موجودی به آن‌ها اضافه شود.

## محدودیت‌های شناخته‌شده (صادقانه بگویم)
- حذف تامین‌کننده از پنل مدیر، فقط پروفایلش را در دیتابیس غیرفعال می‌کند؛ چون حذف واقعی حساب ورود (Firebase Auth) از سمت کاربر نیاز به سرور مدیریتی (Admin SDK) دارد که رایگان نیست. برای اکثر کاربردها همین کافی است چون بدون پروفایل تاییدشده، او دیگر نمی‌تواند محصول اضافه یا سفارش دریافت کند.
- گزارش‌ها روی داده لحظه‌ای محاسبه می‌شوند؛ با رشد فروشگاه (چند هزار سفارش)، بهتر است این محاسبات به یک تابع سمت سرور منتقل شود (باز هم نیاز به پلن پولی Firebase Functions دارد؛ وقتی به آن مقیاس رسیدید بگویید).

# آماده‌سازی برای دیتاسنتر اختصاصی (Ubuntu 24)

پروژه همین الان کاملاً قابل‌انتقال است چون فقط فایل‌های ساکن (HTML/CSS/JS) است — هر جایی که بتواند فایل استاتیک سرو کند (GitHub Pages، یک VPS، هر سروری) کار می‌کند. دیتابیس (Firebase) جدا از محل هاست فرانت است و نیازی به تغییر ندارد مگر خودتان بخواهید کاملاً مستقل شوید.

## پیشنهاد من برای وقتی به این مرحله رسیدید
**فرانت (فایل‌های سایت):**
- یک VPS با اوبونتو ۲۴ + **Nginx** برای سرو فایل‌های استاتیک (سریع و سبک).
- گواهی SSL رایگان با **Certbot** (Let's Encrypt).

**لایه امنیتی:**
- **Cloudflare** (رایگان) جلوی دامنه — فیلتر حملات DDoS و بات‌ها قبل از رسیدن به سرور شما.
- **UFW** روی سرور: فقط پورت‌های ۸۰/۴۴۳/۲۲ باز باشند.
- **Fail2ban**: مسدودسازی خودکار IPهایی که مدام تلاش ناموفق برای ورود SSH دارند.
- آپدیت‌های امنیتی خودکار اوبونتو (`unattended-upgrades`) فعال باشد.

**درباره «هک/تروجان»**: چون این یک وب‌اپ است (نه فایل نصبی)، خطر تروجان کلاسیک عملاً وجود ندارد. نگرانی واقعی، حملات وب است (SQL/کد تزریقی، دسترسی غیرمجاز به داده) که با قوانین امنیتی Firestore (که همین الان داریم) + Cloudflare + به‌روز نگه‌داشتن سرور پوشش داده می‌شود.

**دیتابیس**: می‌توانید همان Firebase بماند (که خودش زیرساخت امنیتی گوگل را دارد و نیازی به نگهداری سرور جداگانه ندارد)، یا اگر واقعاً خواستید کاملاً مستقل شوید، به PostgreSQL روی همان VPS منتقل شود — این یک بازنویسی کامل بک‌اند می‌خواهد و پیشنهادم این است فقط وقتی فروشگاه به مقیاس بزرگ رسید به آن فکر کنیم.

هر وقت آماده انتقال بودید، بگویید تا کانفیگ Nginx و اسکریپت‌های امنیتی را دقیق برایتان بنویسم.

# نسخه سوم: صفحه مشتری کامل، دسته‌بندی پویا، فیلد دلخواه، حساب مشتری، تم و تنظیمات

همه فایل‌ها به‌روز شدند: `index.html`, `app.js`, `style.css`, `supplier.html`, `supplier.js`, `supplier.css`, `admin.html`, `admin.js`, `firebase-config.js` + قوانین Firestore بالا (نسخه نهایی‌تر، حتماً جایگزین کنید).

## خلاصه تغییرات

**۱۳. صفحه مشتری بازطراحی شد**: بالا سرچ (چپ) / «ظرف من» (وسط) / منوی دسته‌بندی (راست، کشویی از راست). زیرش نوار «شگفت‌انگیز» (قرمز/نارنجی، فقط وقتی محصولی تیک ویژه داشته باشد نمایش داده می‌شود)، بعد ردیف آیکون دسته‌ها، بعد شبکه محصولات. پایین صفحه هم نوار ثابت (خانه / دسته‌ها / سبد / حساب من) — دقیقاً مثل ساختار دیجی‌کالا.

**۱۴ و ۱۵. دسته‌بندی و فیلد پویا**: در پنل مدیر تب «دسته‌بندی‌ها» — اضافه/حذف با یک اموجی برای آیکون. در فرم محصول تامین‌کننده: دکمه ➕ برای عکس (هر بار زدن، یک عکس دیگر) و دکمه ➕ برای فیلد دلخواه (هر بار زدن، یک ردیف «نام فیلد + مقدار» اضافه می‌شود، هرکدام هم دکمه حذف کنار خودش دارد). یک تیک «نمایش در پیشنهاد شگفت‌انگیز» هم همان‌جاست.

**۱۷. مدیریت محصول**: بعد از ذخیره، هر محصول دو دکمه «ویرایش» و «حذف» دارد. حذف با **دو تایید پشت‌هم** انجام می‌شود.

**۱۸. بازنشانی**: پنل مدیر → تب «تنظیمات» → پاک‌کردن جداگانه محصولات/سفارش‌ها/پیام‌ها، یا یک دکمه «بازنشانی کامل» (با دو تاییدیه).

**۱۹. شگفت‌انگیز**: تیک روی محصول در فرم تامین‌کننده، همان لحظه در نوار بالای فروشگاه ظاهر می‌شود.

**۲۰. چیدمان الهام از دیجی‌کالا**: توضیح داده شد (بند ۱۳).

**۲۱. حساب سبک مشتری** (⚠️ مهم بخوانید): قبل از پرداخت، مشتری شماره‌اش را می‌زند، یک کد ۴ رقمی تولید می‌شود، وارد می‌کند، تایید می‌شود، بعد صورت‌حساب نهایی و دکمه پرداخت را می‌بیند؛ بعد از ثبت، یک **کد پیگیری** نشان داده می‌شود. در «حساب من» (نوار پایین)، با همان شماره، تاریخچه سفارش‌ها و علاقه‌مندی‌ها دیده می‌شود.

> **این بخش هنوز پیامک واقعی ندارد.** چون اتصال کاوه‌نگار/ملی‌پیامک نیاز به یک سرویس واسط امن دارد (چون کلید API آن‌ها را نمی‌شود مستقیم در کد مرورگر گذاشت — قابل دیدن و سواستفاده می‌شود)، فعلاً یک **حالت آزمایشی** ساخته‌ام: کد تایید همان لحظه روی صفحه (با یک نوار زرد «حالت آزمایشی») نشان داده می‌شود تا کل مسیر را تست کنید. وقتی حساب کاوه‌نگار/ملی‌پیامک ساختید و به من گفتید، این بخش را به پیامک واقعی وصل می‌کنم (به یک واسط رایگان مثل Cloudflare Worker نیاز دارد، در آن مرحله دقیق توضیح می‌دهم).

**۲۲. چند عکس محصول**: توضیح داده شد (بند ۱۴/۱۵).

**۲۳. علاقه‌مندی‌ها**: قلب روی هر کارت محصول؛ لیست در «حساب من» — فقط روی همان گوشی/مرورگر ذخیره می‌شود.

**۲۴. حداقل سفارش و هزینه ارسال**: در پروفایل تامین‌کننده (تب سفارش‌ها) قابل تنظیم است. فعلاً فقط اطلاعاتی است (ذخیره می‌شود، در گزارش‌ها قابل استفاده است) — در محاسبه خودکار جمع سبد اعمال نمی‌شود، چون در مدل فعلی سفارش تا وقتی یک تامین‌کننده آن را قبول نکند مشخص نیست کدام تامین‌کننده آن را می‌فرستد. اگر بخواهید این را هم فعال کنم (مثلاً به‌صورت پیام هشدار به تامین‌کننده هنگام قبول، اگر سفارش زیر حداقلش بود)، بگویید.

**۲۵. خروجی CSV**: پنل مدیر → تنظیمات → «دانلود گزارش سفارش‌ها» — فایل CSV با همه سفارش‌ها (قابل باز کردن در اکسل).

**۲۶. اینماد**: یادآوری شد، در زمان راه‌اندازی واقعی پیگیری می‌کنید.

**تم مشکی/رنگی**: پنل مدیر → تنظیمات → انتخاب تم → اعمال. همان لحظه برای همه بازدیدکنندگان فروشگاه اعمال می‌شود.

## کاری که باید انجام دهید
1. قوانین Firestore بالا (نسخه نهایی) را Publish کنید.
2. فایل‌های تغییر‌کرده را در گیت‌هاب جایگزین کنید.
3. وارد `admin.html` شوید → تب «دسته‌بندی‌ها» → چند دسته اضافه کنید (مثلاً همان‌هایی که قبلاً داشتید: یکبار مصرف، چینی و سرامیک، شیشه‌ای، استیل). این لیست از اول خالی است چون دیگر در کد ثابت نیست.

# اصلاح: موجودی هرگز به مشتری نشان داده نمی‌شود

فایل‌های تغییر‌کرده: `app.js`, `supplier.js`, `admin.js`, `supplier.css` + یک اصلاح کوچک در قوانین Firestore بالا (خط مربوط به `products` → `allow update`، دوباره Publish کنید).

## چطور کار می‌کند حالا
- عدد موجودی (`stock`) دیگر هیچ‌وقت باعث «ناموجود» نمایش‌دادن به مشتری نمی‌شود. مشتری می‌تواند هر تعدادی که بخواهد سفارش بدهد، حتی بیشتر از موجودی ثبت‌شده.
- وقتی سفارش به تامین‌کننده‌ای می‌رسد که تعداد درخواستی از موجودی ثبت‌شده‌اش بیشتر است، یک **هشدار زرد** فقط برای خود او در همان کارت سفارش نشان داده می‌شود: «فلان کالا: موجودی ثبت‌شده X عدد است، Y عدد کسری دارید — لطفاً تامین کنید.»
- اگر تامین‌کننده اصلاً نتواند آن کالا را در بازار پیدا کند، در پنل خودش (یا شما در تب «موجودی») دکمه **«اتمام موجودی در بازار»** را می‌زند — فقط از همین لحظه، آن محصول برای مشتری «ناموجود» نشان داده می‌شود. با زدن دوباره همان دکمه («بازگرداندن»)، دوباره قابل‌خرید می‌شود.

این یعنی مشتری هیچ‌وقت متوجه کمبود لحظه‌ای موجودی نمی‌شود — فقط وقتی که واقعاً و رسماً اعلام «اتمام در بازار» شده باشد.

# ماژول حساب‌داری (عمده‌فروشی)

فایل‌های جدید: `accounting.html`, `accounting.js`, `accounting.css` — کاملاً مستقل و اپن‌سورس (بدون هیچ سرویس بیرونی یا کتابخانه بسته)، فقط از همان Firebase شما استفاده می‌کند. فعلاً از پنل مدیر (`admin.html`) یک لینک «حساب‌داری» به آن اضافه شده؛ هر جای دیگری هم خواستید (مثلاً یک تب کاملاً جدا، یا داخل خود admin.html ادغام شود) بگویید تا جابه‌جا کنم.

## چه چیزی می‌سازد
- **اشخاص**: هر مشتری/تامین‌کننده/شخص دیگر یک «حساب معین» جدا دارد؛ می‌توانید مانده اولیه هم برایش ثبت کنید.
- **صورت‌حساب هر شخص**: ثبت سند بدهکار/بستانکار دستی (تاریخ + شرح + مبلغ)، با محاسبه خودکار مانده بعد از هر سند.
- **چک‌ها**: ثبت چک دریافتی (از مشتری) یا پرداختی (به تامین‌کننده) با شماره، بانک و تاریخ سررسید؛ وضعیت: در جریان / وصول‌شده / برگشتی.
- **سررسید پرداخت**: لیست چک‌های در جریان به ترتیب نزدیک‌ترین تاریخ؛ سررسیدهای گذشته با رنگ قرمز مشخص می‌شوند.
- **گزارش کلی**: مجموع بدهکاران، مجموع بستانکاران، خالص وضعیت مالی، و لیست کامل هرکدام.

## یک نکته طراحی مهم
عمداً ثبت چک را از سند بدهکار/بستانکار **جدا** نگه داشتم — یعنی وصول‌شدن یک چک خودش را در صورت‌حساب شخص ثبت نمی‌کند مگر شما دستی یک سند برایش بزنید. این برای این است که کنترل کامل دست خودتان باشد (چون روش‌های حسابداری برای زمان ثبت چک متفاوت است). اگر ترجیح می‌دهید وصول چک خودکار یک سند بستانکار/بدهکار هم بسازد، بگویید تا وصل کنم.

## کاری که باید انجام دهید
1. قوانین Firestore بالا (شامل سه کالکشن جدید `acc_persons`, `acc_transactions`, `acc_checks`) را Publish کنید.
2. فایل‌های جدید را در گیت‌هاب آپلود کنید.
3. از `admin.html`، دکمه «حساب‌داری» بالای صفحه را بزنید (همان ایمیل مدیر + کد تایید همیشگی).

## نکته امنیتی
این سه کالکشن فقط برای مدیر (شما) قابل خواندن و نوشتن است — نه تامین‌کننده‌ها، نه مشتری‌ها. داده‌های مالی حساس اینجا از بقیه پروژه جداست.

> این بخش‌ها را عمداً در دکمه‌های «بازنشانی» (Reset) پنل تنظیمات قرار ندادم، چون داده حسابداری واقعی است، نه داده آزمایشی — پاک نمی‌شود مگر خودتان از داخل خود صفحه حساب‌داری تک‌تک حذف کنید.

- بررسی «اجازه پرداخت چکی دارد؟» با وجود سند در `trustedCustomers` چک می‌شود (مطابق چیزی که در مرحله ۴ واقعاً نوشته می‌شود).
- بررسی «اعتبار باقیمانده دارد؟» مستقیم از `creditAccounts/{شماره}` (سقف منهای مصرف‌شده) خوانده می‌شود.
- **یک حفره مهم هم پر شد**: قبلاً وقتی سفارش اعتباری قبول می‌شد، هیچ‌جا از سقف مشتری کم نمی‌شد (یعنی عملاً سقف اعتبار اجرا نمی‌شد)! حالا «قبول سفارش» برای خرید اعتباری، هم سقف باقیمانده را چک می‌کند (اگر کافی نبود، خطا می‌دهد) و هم به‌صورت خودکار مبلغ را به «مصرف‌شده» مشتری اضافه می‌کند.

## کاری که باید انجام دهید
فایل‌های `app.js` و `admin.js` را در گیت‌هاب جایگزین کنید، و یک سفارش آزمایشی تست کنید (هر سه روش پرداخت: فیش، چک، اعتباری) تا مطمئن شوید درست ثبت و قابل قبول‌کردن است.

بگویید «مرحله ۶» تا پاکسازی نهایی (حذف تب‌های قدیمی و فایل‌های `supplier.*`) را هم انجام دهم.

# مرحله ۵ از تبدیل به «تک‌مدیر» — تحویل شد

بررسی کامل `app.js` (سمت مشتری) انجام شد — از قبل کاملاً با مدل تک‌مدیره هماهنگ بود:
- دیگر هیچ کوئری‌ای به کالکشن `suppliers` نمی‌زند (که بعد از مرحله ۱ حذف شده بود و باعث خطا می‌شد)
- شناسه شما (مدیر) از طریق `settings/site` خوانده می‌شود (هر بار که وارد پنل مدیر می‌شوید، خودکار به‌روز می‌ماند)
- بررسی «مشتری معتبر برای چک» و «سقف اعتبار» دقیقاً با همان ساختار ساده مرحله ۱ و ۴ هماهنگ است

فایلی برای جایگزینی لازم نیست.

**یک نکته کوچک باقی‌مانده برای مرحله ۶:** در فوتر منوی فروشگاه (`index.html`) هنوز یک لینک «پنل تامین‌کنندگان» هست که باید حذف شود — در مرحله آخر همراه با حذف کامل فایل‌های تامین‌کننده انجامش می‌دهم.

بگویید «مرحله ۶» تا کار را تمام کنم: حذف تب‌های قدیمی، حذف لینک، و راهنمای حذف فایل‌های `supplier.html/js/css` از گیت‌هاب.

# مرحله ۶ از تبدیل به «تک‌مدیر» — پایانی ✅

فایل‌های تغییر‌کرده: `index.html` (حذف لینک پنل تامین‌کننده)، `sw.js`، `firebase-config.js` (شماره نسخه به‌روز شد)

## چه چیزی عوض شد
- تب‌ها و کد «تامین‌کنندگان» و «پیام‌رسانی» در `admin.js`/`admin.html` — از مراحل قبل پاک بودند، چیز اضافه‌ای برای حذف نماند
- لینک «پنل تامین‌کنندگان» از منوی فروشگاه حذف شد
- فایل‌های `supplier.html` و `supplier.js` از این زیپ **حذف شدند** (دیگر لازم نیستند)
- `supplier.css` **نگه داشته شد** — با وجود اسمش، یک فایل استایل مشترک است که `index.html`, `admin.html`, `accounting.html` هم از آن استفاده می‌کنند؛ حذفش ظاهر همه صفحات را خراب می‌کند

## کاری که باید انجام دهید (قدم آخر migration)
1. فایل‌های `index.html`, `sw.js`, `firebase-config.js` را در گیت‌هاب جایگزین کنید.
2. در گیت‌هاب، فایل‌های `supplier.html` و `supplier.js` را **حذف** کنید (روی فایل در گیت‌هاب بروید → آیکون سطل زباله → Commit).
3. `supplier.css` را **نگه دارید** — پاک نکنید.
4. اگر قوانین Firestore مرحله ۱ را هنوز Publish نکرده‌اید، همین الان Publish کنید.

## جمع‌بندی کل migration
پروژه «ظرف من» از یک بازارگاه چندتامین‌کننده‌ای (با صف هدایت سفارش، تایید تامین‌کننده، چت مدیر-تامین‌کننده) به یک فروشگاه تک‌مالک ساده‌تر تبدیل شد: شما مستقیماً محصول اضافه می‌کنید، سفارش می‌گیرید، پرداخت (فیش/چک/اعتباری) را تایید می‌کنید، و همه گزارش‌ها را در یک پنل می‌بینید — بدون پیچیدگی مدیریت چند تامین‌کننده جداگانه.
